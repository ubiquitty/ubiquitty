# Core PGO profiles

Training profile for optimized Core builds.

Linux x86-64 targets use `linux-x86_64-core.profdata`; Linux aarch64 targets use
`linux-aarch64-core.profdata`. macOS and other targets retain
`portable-core.profdata`. Selection follows the compiler target.

Profiles are generated by Scripts/pgo-train.sh (instrumented bench_stack and
bench_ingest_corpora, llvm-profdata merge) and consumed via
-fprofile-use by every optimised CMake build (Scripts/build-host.sh,
build-agent.sh, build-linux-gtk.sh and a hand-run Release configure) and by
Scripts/build-macos.sh and Scripts/run-bench.sh. UBIQUITTY_PGO=OFF disables it
in each of them; -DUBIQUITTY_PGO=OFF does the same for a hand-run configure.

An explicit `UBQ_PGO_PROFILE` overrides the shell consumer's default.
`-DUBIQUITTY_PGO_PROFILE=/path/to/profile.profdata` overrides CMake's default;
caller-provided `-fprofile-use` flags remain authoritative. Existing CMake cache
entries are preserved. Pass `-UUBIQUITTY_PGO_PROFILE` to select the target's
default when reconfiguring an existing build directory.

Native retraining updates the target's profile and its matching `.trained-at`,
`.trained-tree` and `.drift-budget` sidecars. `UBQ_PGO_TRAIN_OUT=/path/to/private.profdata`
selects a private output instead. The consumer override `UBQ_PGO_PROFILE` does
not redirect training output.

Linux profiles also carry `.trained-toolchain`: the image content digest,
recipe digest, compiler version, target and profile SHA256. Both shell and
CMake consumers verify it. Native Linux builds outside the release image
report `PGO: NOT APPLIED` and build without PGO; `REQUIRE` refuses them.
Profiled development and performance builds must run through
`UBQ_CI_LINUX_IMAGE=true Scripts/ci-linux-image.sh`, with
`PATH="$UBQ_PGO_LLVM:$PATH"` and `CXX=clang++` set inside the container.
Unprofiled comparisons use `UBIQUITTY_PGO=OFF`. There is no separately maintained
host-compiler profile. `build-perf-bench.sh` and `run-bench.sh` default to
`REQUIRE`: a missing or mismatched profile refuses the benchmark build. Use
`UBIQUITTY_PGO=OFF` explicitly for an unprofiled measurement.

Only a clang reads it, and only a clang at least as new as the llvm-profdata
that wrote it: the file carries LLVM's indexed-format version. The CMake builds
and the scripts that take their flags from Scripts/pgo-flags.sh
(build-macos.sh, build-perf-bench.sh, run-bench.sh) ask the compiler to read the profile
before handing it over; a compiler that cannot builds without it and says
`PGO: NOT APPLIED`. `UBIQUITTY_PGO=REQUIRE` turns that into a failed configure.

In CI the Linux profiles are read by the LLVM that `UBQ_PGO_LLVM` names
in the CI image (`Scripts/ci-linux-image.sh`), not by the image's default
clang. The Linux pgo stage and the release AppImage build both run with
`UBIQUITTY_PGO=REQUIRE`. Format compatibility alone is insufficient: packaging
also requires zero discarded counters in the recorded-budget check. Preserve
the validated image by content digest; rebuilding a recipe can resolve newer
compiler packages and requires new profiles.

Commit profile retraining separately from unrelated source changes so its
code-generation and performance effects can be attributed.

## Training work

`Scripts/pgo-train.sh` trains on a fixed schedule of `bench_stack` and
`bench_ingest_corpora` work and describes it in its header. Training timings
are not performance evidence; validate a profile change with an independent
workload.

## Drift

A profile describes the tree it was trained on. An edit that changes a
function's control flow moves the hash the compiler matches its counters by;
`-fprofile-use` then discards those counters and compiles the function cold,
and every build path passes `-Wno-backend-plugin`, so nothing says so.
`Scripts/check-pgo-applies.py` compiles the portable-core units with that
diagnostic restored and adds up the counters the compiler discarded. Two bounds
read that number, both in `Scripts/pre-push-gates.sh`:

- **Per push.** The units a branch changed are compiled against the profile
  here and at the merge base with `origin/main`, and the push is refused when
  the branch newly detaches more than 30,000 counters. The figure and its
  measurement are at the call site. This bound compiles only changed units, so
  an edit to a header that reshapes the functions inlining it compiles nothing
  here and reads zero.
- **In total.** Every unit is compiled against the profile, and the push is
  refused when the discarded total exceeds the drift budget recorded in
  `<profile>.drift-budget`. `Scripts/pgo-train.sh` writes that sidecar at every
  retrain: the total the fresh profile discards, which is zero or the training
  run failed, plus an allowance of 300,000 counters. `check-pgo-applies.py`
  records the measurements behind the allowance. From 60% of the budget the
  gate prints `check-pgo-applies: WARNING — …` and passes; the pre-push runner
  repeats that line beside the pass on every push until a retrain lands. A
  profile with no `.drift-budget` beside it stands down here, by name, in the
  push's skipped list. A sidecar recorded for another Source/ tree than
  `.trained-tree` names is refused, because reading it as absent would switch
  the bound off at the retrain that should have reset it.

The sidecars beside each profile:

| Sidecar | Contents | Read by |
| --- | --- | --- |
| `.trained-at` | the commit the profile was trained at | `Scripts/pgo-staleness.sh` |
| `.trained-tree` | the Source/ tree it describes | `Scripts/pgo-staleness.sh`, `Scripts/check-pgo-applies.py` |
| `.drift-budget` | the tree the budget is keyed to, the baseline, the bound | `Scripts/check-pgo-applies.py --recorded-budget` |
| `.trained-toolchain` | Linux image, compiler, target and profile digest | Linux consumers and applicability checks |

`.trained-at` is the HEAD of the checkout the training ran in. A retrain by
`Scripts/pgo-retrain-check.sh --retrain` runs at an `origin/main` commit, which
stays in main's history; a profile trained on a branch names that branch's
commit, which a rebase merge replaces, and a clone whose history starts after
the training never has the commit named. Where the commit is missing,
`pgo-staleness.sh` counts from the profile's own commit.
`.trained-tree` names content rather than history: it equals
`git rev-parse <commit>:Source` at any commit whose Source/ is the tree the
profile was trained on, in whichever repository holds one. Neither pointer
reproduces the profile's bytes; `Scripts/pgo-train.sh` generates a profile for
the tree that is checked out.

## Retraining

`Scripts/pgo-retrain-check.sh` reports the profile's standing — how far the
tree has moved and the discarded total against the budget — and exits 1 when a
retrain is due. `--retrain` performs it: `Scripts/pgo-train.sh` in a fresh
worktree of `origin/main` (`--base REF` for another), then the profile and its
sidecars in one commit and nothing else (`Scripts/check-pgo-commit-shape.py`),
on a branch `pgo/retrain-<date>`. It never pushes; push the branch and land it
as its own commit.

On Linux, training, retraining and applicability checks automatically enter
the native release image through `Scripts/ci-linux-image.sh`. Set
`UBQ_BUILD_ROOT` and `CCACHE_DIR` to persistent, Docker-accessible directories.
For native aarch64 Linux training from macOS with Docker, one command is:

```sh
UBQ_PGO_PLATFORM=Linux Scripts/pgo-retrain-check.sh --retrain --base HEAD
```

The Linux x86-64 command is the same without `UBQ_PGO_PLATFORM`. macOS training
without that override continues to use Xcode and the portable profile.
`UBQ_PGO_RETRAIN_BRANCH` and `UBQ_PGO_RETRAIN_WORKTREE` select distinct output
branches and worktrees when training several profiles on the same day.

Cadence: weekly, and as soon as the pre-push gate prints its warning line. The
gate refuses before a push lands a profile past its budget, so a missed week
costs a refused push rather than a cold build.

The weekly run is a launchd agent on the Mac that trains the portable profile:
`org.ubiquitty.pgo-retrain-check.plist`, beside this file, runs
`Scripts/pgo-weekly.sh` on Sundays at 03:00. The wrapper works in a clone of
its own, `~/Projects/ubq-pgo-weekly`. It refuses to start with under 15 GiB
free, fetches and detaches the clone at `origin/main`, runs the report at
nice 10, and runs `--retrain` only when the report exits 1, so a retrain
leaves its commit on `pgo/retrain-<date>` in that clone and pushes nothing.
Everything it prints goes to `~/Library/Logs/ubiquitty-pgo-weekly.log`. Make
the clone once with `git clone <the repository's URL> ~/Projects/ubq-pgo-weekly`,
then install the agent with
`cp Support/pgo/org.ubiquitty.pgo-retrain-check.plist ~/Library/LaunchAgents/`
and
`launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/org.ubiquitty.pgo-retrain-check.plist`.
Disable it with `launchctl bootout gui/$(id -u)/org.ubiquitty.pgo-retrain-check`,
and delete the copied plist so it does not load again at the next login.

The retrain is not a CI job. The profile is trained on the machine class that
consumes it, with Linux training inside the release image and macOS training
using Xcode. The workflows run with read-only tokens and
`persist-credentials: false`, so no job has a path to commit or push a result
(`Docs/building-and-releasing.md`, "Runners and fork pull requests").
